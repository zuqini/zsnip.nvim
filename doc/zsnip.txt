1. INTRODUCTION                                            *zsnip-introduction*

Neovim ships |vim.snippet|: it expands an LSP snippet body, runs the session,
and moves between tabstops. What it does not ship is everything around that --
finding the snippet packages on your 'runtimepath', reading the two formats
they come in, deciding which ones a filetype gets, and handing them to a
completion menu.

zsnip is that layer and nothing more. There is no second snippet engine here
and no format of its own: bodies go to |vim.snippet.expand()| as written.

What zsnip adds on top of the engine:

- Both pack formats: VSCode packages with a package.json manifest, and
  snipmate .snippets files including their `extends` lines.
- The variables Neovim does not resolve. Core knows the TM_* set and turns
  every other variable into a tabstop holding its own name; zsnip resolves the
  date, workspace, comment-marker, clipboard, UUID and RANDOM families first.
- Bodies core cannot parse are dropped on load, rather than raising at accept
  time after the completion engine has already deleted the typed word.
- `${0:text}` is renumbered past the last real tabstop, so a placeholder on
  the exit point is reachable.
- Native sources for blink.cmp and nvim-cmp, and an in-process LSP server for
  everything else -- including Neovim's own completion, with no plugin at all.

3. QUICK START                                              *zsnip-quickstart*

>lua
    require('zsnip').setup()

    require('zsnip.loaders.from_vscode').lazy_load()
    require('zsnip.loaders.from_snipmate').lazy_load()

    require('zsnip').start_lsp_server()
<
Nothing is read at startup. A package is scanned and decoded the first time a
filetype it covers is opened, and the 'runtimepath' is re-checked on every
lookup, so a plugin that loads on a filetype and brings its own snippets is
picked up the moment it arrives.

4. CONFIGURATION                                         *zsnip-configuration*

                                                                *zsnip.setup()*
zsnip.setup({opts})

Optional -- every default works without it. Stores options and creates
|:ZSnip|.

>lua
    require('zsnip').setup({
      extend = {},              -- filetype -> filetypes it inherits from
      global_filetype = 'all',  -- bucket every filetype inherits; false to disable
      max_items = 100,          -- default cap for completion_items(); the
                                -- built-in sources ask for an uncapped
                                -- list and filter it themselves
      documentation = true,     -- attach the body as item documentation
      command = true,           -- create :ZSnip
    })
<
==============================================================================
5. LOADERS                                                      *zsnip-loaders*

                                             *zsnip.loaders.from_vscode*
                                             *zsnip.loaders.from_snipmate*
>lua
    require('zsnip.loaders.from_vscode').lazy_load({opts})
    require('zsnip.loaders.from_snipmate').lazy_load({opts})
<
Register a loader. `lazy_load()` defers every read until a filetype asks for
it; `load()` takes the same options but scans and decodes everything up front.

Options:
    paths     string|string[]  Directories to read besides the 'runtimepath'
    include   string[]         Only load these languages
    exclude   string[]         Load every language except these

A VSCode path is a directory containing a package.json. A snipmate path is a
directory containing *.snippets files, or per-filetype directories of them.
Repeated calls merge rather than replace.

                                                      *zsnip.filetype_extend()*
zsnip.filetype_extend({filetype}, {inherits})

Give {filetype} everything registered for {inherits} (a filetype or a list).
Cycles are safe. Every filetype also inherits the `global_filetype` bucket,
and snipmate `extends` lines are honoured as written.

6. SNIPPETS FROM LUA                                       *zsnip-lua-snippets*

                                                         *zsnip.add_snippets()*
zsnip.add_snippets({filetype}, {snippets})

>lua
    require('zsnip').add_snippets('lua', {
      { prefix = 'req', body = "local ${1:mod} = require '$1'" },
      { prefix = 'stamp', body = function() return os.date('%Y-%m-%d') end },
    })
<
A snippet is `{ prefix, body, description? }`. `body` is LSP snippet syntax,
or a function returning it -- called each time the snippet is used, with nil
(or a raise, or an unparseable result) meaning "skip this one". A function
body cannot react to what is typed `into` a tabstop: |vim.snippet| owns the
session and offers no hook for that.

Snippets added here come before file-loaded ones for the same filetype, so a
config can shadow a pack.

7. COMPLETION                                                *zsnip-completion*

Three ways to offer the snippets. Pick one -- a native source for your engine,
or the LSP server. Running both offers every snippet twice.

                                                                 *zsnip.blink*
blink.cmp~
>lua
    require('blink.cmp').setup({
      snippets = { preset = 'default' },
      sources = {
        default = { 'lsp', 'path', 'zsnip', 'buffer' },
        providers = { zsnip = { name = 'zsnip', module = 'zsnip.blink' } },
      },
    })
<
Leave blink's own built-in `snippets` source out of `default`: it reads the
same VSCode packs and cannot see the snipmate ones. The provider `opts` accept
`limit`, `documentation` and `filter`. The module requires nothing from blink.

                                                                   *zsnip.cmp*
nvim-cmp~
>lua
    require('zsnip.cmp').register()

    require('cmp').setup({
      snippet = { expand = function(args) vim.snippet.expand(args.body) end },
      sources = { { name = 'nvim_lsp' }, { name = 'zsnip' } },
    })
<
The `snippet.expand` line is what makes nvim-cmp use Neovim's engine. nvim-cmp
is required by `register()` only, so the module loads without it.

                                                     *zsnip.start_lsp_server()*
zsnip.start_lsp_server({opts})

Start an in-process language server answering `textDocument/completion` with
the snippets of the requesting buffer's filetype, and attach it to every
buffer that gets a filetype. Idempotent.

Options:
    name                string    Client name (default "zsnip")
    filetypes           string[]  Attach only to these filetypes
    limit               integer   Cap on items per response (default: uncapped)
    documentation       boolean   Attach the body as item documentation
    filter              fun       Keep only the snippets it returns true for
    trigger_characters  string[]  Characters that make a client ask unprompted

blink.cmp and nvim-cmp can receive the snippets this way too, through their
existing LSP source, at the cost of no longer being able to configure snippets
separately from language-server items. For Neovim's own completion, name the
trigger characters -- |vim.lsp.completion| reads them to decide when to ask:

A trigger can begin with any printable character -- `2x1table` and `#!` are
both real friendly-snippets triggers -- so a letters-only list leaves the first
firing a keystroke late and the second never firing at all.
>lua
    local triggers = {}
    for byte = 33, 126 do
      triggers[#triggers + 1] = string.char(byte)
    end

    require('zsnip').start_lsp_server({ trigger_characters = triggers })

    vim.api.nvim_create_autocmd('LspAttach', {
      callback = function(args)
        vim.lsp.completion.enable(true, args.data.client_id, args.buf, { autotrigger = true })
      end,
    })
<
                                                     *zsnip.completion_items()*
zsnip.completion_items({opts})

Snippets as |lsp.CompletionItem|s, for a hand-rolled completion source. Items
carry `insertTextFormat = Snippet` and a resolved `insertText`. One item per
trigger.

Options:
    prefix         string   Fuzzy-match triggers against this
    filetype       string   Defaults to the filetype of {bufnr}
    bufnr          integer  Defaults to the current buffer
    limit          integer  Overrides `max_items`
    documentation  boolean  Overrides the configured default
    filter         function  Keep only the snippets it returns true for;
                             runs before matching and before `limit`

8. API                                                              *zsnip-api*

                                                                  *zsnip.get()*
zsnip.get({filetype})
    Every snippet available to a filetype, in shadowing order. Defaults to the
    current buffer's filetype. Each entry carries a `filetype` field naming
    where it came from.

                                                            *zsnip.available()*
zsnip.available()
    Every filetype zsnip knows snippets for, mapped to them.

                                                              *zsnip.resolve()*
zsnip.resolve({body})
    Resolve the variables Neovim does not know in an arbitrary body.

                                                               *zsnip.reload()*
zsnip.reload()
    Forget everything read from disk; the next lookup rescans. Snippets added
    through |zsnip.add_snippets()| survive.

                                                                *zsnip.match()*
zsnip.match()
    The snippet whose trigger ends at the cursor, longest trigger first. A
    trigger starting with a keyword character has to start a word, so `x` does
    not fire in the middle of `max`.

                                                           *zsnip.expandable()*
                                                               *zsnip.expand()*
zsnip.expandable()
zsnip.expand()
    Whether the trigger before the cursor can be expanded, and expanding it.

                                                       *zsnip.expand_snippet()*
zsnip.expand_snippet({snippet})
    Expand a snippet table at the cursor, trigger or not.

                                                       *zsnip.expand_or_jump()*
zsnip.expand_or_jump()
    Expand what is under the cursor, otherwise jump to the next tabstop. The
    one binding most configs want:
>lua
    vim.keymap.set({ 'i', 's' }, '<C-k>', function()
      require('zsnip').expand_or_jump()
    end)
<
                                                                 *zsnip.jump()*
                                                             *zsnip.jumpable()*
                                                               *zsnip.active()*
                                                                 *zsnip.stop()*
zsnip.jump({direction})
zsnip.jumpable({direction})
zsnip.active({filter})
zsnip.stop()
    Thin wrappers over |vim.snippet|, so a config can bind one namespace.
    `jump()` returns whether it moved.

zsnip installs no keymaps of its own -- every completion engine already has an
opinion about <Tab>.

9. COMMANDS                                                    *zsnip-commands*

                                                                       *:ZSnip*
:ZSnip [expand]     Pick a snippet for the current filetype and expand it.
:ZSnip list         Show every snippet the current filetype has, and which
                    filetype each came from.
:ZSnip reload       Forget everything read from disk and rescan.

10. HEALTH                                                       *zsnip-health*

>vim
    :checkhealth zsnip
<
Reports the Neovim version, whether |vim.snippet| and the snippet grammar are
available, which loaders are registered, and how many snippets were actually
found.

The last section, "Completion sources", answers the other half of "why do I
see no snippets": a snippet that was found still has to reach a menu. It
reports whether |zsnip.start_lsp_server()| has been called, and whether a
client is actually running -- a `filetypes` list that excluded every buffer,
or a `:LspStop`, leaves the server registered but serving nothing. If you
registered a native source (`zsnip.blink` or `zsnip.cmp`) instead, no LSP
server is the correct state.

11. COMING FROM LUASNIP                                         *zsnip-luasnip*

The loader and registry API is deliberately shaped like LuaSnip's:

    luasnip.loaders.from_vscode.lazy_load()  ->  zsnip.loaders.from_vscode.lazy_load()
    luasnip.loaders.from_snipmate.lazy_load()->  zsnip.loaders.from_snipmate.lazy_load()
    ls.add_snippets(ft, ...)                 ->  zsnip.add_snippets(ft, ...)
    ls.filetype_extend(ft, ...)              ->  zsnip.filetype_extend(ft, ...)
    ls.expand_or_jump() / ls.jumpable()      ->  zsnip.expand_or_jump() / zsnip.jumpable()

LuaSnip's snippet node DSL (`s`, `i`, `t`, `f`, `c`, `d`) has no equivalent:
|vim.snippet| takes a snippet body as text and owns the session, so a body is
either LSP snippet syntax or a function returning it.
