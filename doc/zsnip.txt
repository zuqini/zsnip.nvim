1. INTRODUCTION                                            *zsnip-introduction*

Neovim ships |vim.snippet|: it expands an LSP snippet body, runs the session,
and moves between tabstops. What it does not ship is everything around that --
finding the snippet packages on your 'runtimepath', reading the two formats
they come in, deciding which ones a filetype gets, and handing them to a
completion menu.

zsnip is that layer and nothing more. There is no second snippet engine here
and no format of its own: bodies go to |vim.snippet.expand()| as written.

What zsnip adds on top of the engine:

- Both pack formats: VSCode packages with a package.json manifest, and
  snipmate .snippets files including their `extends` lines.
- The variables Neovim does not resolve. Core knows the TM_* set and turns
  every other variable into a tabstop holding its own name; zsnip resolves the
  date, workspace, comment-marker, clipboard, UUID and RANDOM families first,
  in all four spellings -- $VAR, ${VAR}, ${VAR:default} and
  ${VAR/regex/format/}.
- Bodies core cannot take are dropped on load, rather than raising at accept
  time after the completion engine has already deleted the typed word. That
  covers both the ones the grammar rejects and the ones it accepts that
  |vim.snippet.expand()| then asserts on -- a second $0, or two placeholders
  that disagree about a tabstop.
- Triggers that are not words -- `<div`, `#!`, `console.log`. Every source
  tells the menu to replace the whole non-blank run before the cursor, so such
  a trigger is offered at all and lands over what you typed.
- `${0:text}` is renumbered past the last real tabstop, so a placeholder on
  the exit point is reachable.
- Bodies written with CRLF. |vim.snippet.expand()| splits on `\n` alone, so a
  body shipping Windows line endings lands a literal ^M on the end of every
  inserted line but the last; zsnip collapses them on load, and on a clipboard
  value, which arrives after that point.
- Four ways to serve them: native sources for blink.cmp and nvim-cmp, an
  in-process LSP server for any menu that speaks LSP, and a `'complete'`
  function source for Neovim's own completion, with no plugin at all.

3. QUICK START                                              *zsnip-quickstart*

>lua
    require('zsnip').setup()

    require('zsnip.loaders.from_vscode').lazy_load()
    require('zsnip.loaders.from_snipmate').lazy_load()

    require('zsnip').start_lsp_server()
<
Nothing is read at startup. A package is scanned and decoded the first time a
filetype it covers is opened, and the 'runtimepath' is re-checked on every
lookup, so a plugin that loads on a filetype and brings its own snippets is
picked up the moment it arrives.

4. CONFIGURATION                                         *zsnip-configuration*

                                                                *zsnip.setup()*
zsnip.setup({opts})

Optional -- every default works without it. Stores options and creates
|:ZSnip|.

>lua
    require('zsnip').setup({
      extend = {},              -- filetype -> filetypes it inherits from
      global_filetype = 'all',  -- bucket every filetype inherits; false to disable
      max_items = 100,          -- default cap for completion_items() and
                                -- for zsnip.complete; math.huge means
                                -- uncapped; blink/cmp/lsp ask for an
                                -- uncapped list and filter it
      documentation = true,     -- attach the body and description to items
      command = true,           -- create :ZSnip
    })
<
An unknown key, or a known one of the wrong type, is reported with
|vim.notify()| and dropped -- the rest of the config still applies, and the
default is used in its place. So is a known key whose value it cannot use
(`global_filetype = true`, a fractional or negative `max_items`).
`command = false` removes an existing |:ZSnip| as well as declining to
create one, so a later setup() can undo an earlier one.

5. LOADERS                                                      *zsnip-loaders*

                                             *zsnip.loaders.from_vscode*
                                             *zsnip.loaders.from_snipmate*
>lua
    require('zsnip.loaders.from_vscode').lazy_load({opts})
    require('zsnip.loaders.from_snipmate').lazy_load({opts})
<
Register a loader. `lazy_load()` defers every read until a filetype asks for
it; `load()` takes the same options but scans and decodes everything up front.

Comments and trailing commas are accepted in VSCode snippet JSON. VSCode
generates every user snippet file with a `//` header block, and strict JSON
would reject the file -- and every snippet in it -- for that alone.

Options:
    paths     string|string[]  Directories to read besides the 'runtimepath'
    include   string|string[]  Only load these languages
    exclude   string|string[]  Load every language except these

A snipmate path is a directory containing *.snippets files, or per-filetype
directories of them. Repeated calls merge rather than replace. `_.snippets` --
snipmate's convention for "every filetype", which honza/vim-snippets ships one
of -- is filed under `global_filetype` instead of a filetype literally named
`_`, and dropped entirely when `global_filetype` is `false`. `${VISUAL}`/
`$VISUAL`, snipmate's own name for the selected text, is rewritten to
`TM_SELECTED_TEXT` on the way in. A VSCode pack's spelling of "every filetype"
is the language `all` -- in a manifest's `language` list or a `.code-snippets`
entry's `scope` -- and it is filed under `global_filetype`, or dropped, the
same way.

A VSCode path is a directory containing a package.json, or one holding loose
snippet files the way VSCode keeps a user's own -- point one at
~/.config/Code/User/snippets and it reads what is already there:

    <language>.json    the filetype the file is named after
    *.code-snippets    the languages each snippet's `scope` names, comma
                       separated; an entry with no scope reaches every
                       filetype, through `global_filetype`
    package.json       still decides when present, and the files it names
                       are not read a second time from the glob

`scope` decides which languages a file serves in the *.code-snippets row
alone. A <language>.json takes its filetype from its filename and a
manifest-declared file takes its from the manifest, and a `scope` key inside
one of those is ignored rather than filtered on -- real packs carry TextMate
scopes (`source.lua`) there harmlessly, and filtering on them drops most of
what the pack serves.

Loose files are only looked for under a configured path. A plugin on the
'runtimepath' declares what it contributes in a package.json, and globbing
every plugin directory for stray JSON would turn up much that is not a
snippet.

Either loader follows symlinks under a configured path: a snippet file that is
one is read like any other, so a stow or dotfiles setup that routes every file
through a link is found rather than passed over. A symlinked directory is
descended into by the snipmate loader alone, whose per-filetype directories
sit below the configured one; a VSCode loose file has to sit in the configured
directory itself, link or not. A link pointing at nothing is skipped.

                                                      *zsnip.filetype_extend()*
zsnip.filetype_extend({filetype}, {inherits})

Give {filetype} everything registered for {inherits} (a filetype or a list).
Cycles are safe. Every filetype also inherits the `global_filetype` bucket,
and snipmate `extends` lines are honoured as written. A dotted filetype such
as `javascript.glimmer` -- which Neovim assigns itself for some filetypes, and
which users set for others, e.g. `yaml.ansible` -- also gets everything
registered for each dot-separated component, after its own and before
`global_filetype`.

6. SNIPPETS FROM LUA                                       *zsnip-lua-snippets*

                                                         *zsnip.add_snippets()*
zsnip.add_snippets({filetype}, {snippets})

>lua
    require('zsnip').add_snippets('lua', {
      { prefix = 'req', body = "local ${1:mod} = require '$1'" },
      { prefix = 'stamp', body = function() return os.date('%Y-%m-%d') end },
    })
<
A snippet is `{ prefix, body, description? }`. `body` is LSP snippet syntax,
or a function returning it -- called each time the snippet is used, with nil
(or a raise, or an unparseable result) meaning "skip this one". A function
body cannot react to what is typed `into` a tabstop: |vim.snippet| owns the
session and offers no hook for that.

Snippets added here come before file-loaded ones for the same filetype, so a
config can shadow a pack.

7. COMPLETION                                                *zsnip-completion*

Four ways to offer the snippets. Pick one -- a native source for your engine,
the in-process LSP server, or Neovim's own completion. Running two offers
every snippet twice.

Only the last two need no completion plugin, and |zsnip.complete| needs no LSP
client either.

                                                                 *zsnip.blink*
blink.cmp~
>lua
    require('blink.cmp').setup({
      snippets = { preset = 'default' },
      sources = {
        default = { 'lsp', 'path', 'zsnip', 'buffer' },
        providers = { zsnip = { name = 'zsnip', module = 'zsnip.blink' } },
      },
    })
<
Leave blink's own built-in `snippets` source out of `default`: it reads the
same VSCode packs and cannot see the snipmate ones. The provider `opts` accept
`limit`, `documentation` and `filter`. The module requires nothing from blink.

                                                                   *zsnip.cmp*
nvim-cmp~
>lua
    require('zsnip.cmp').register()

    require('cmp').setup({
      snippet = { expand = function(args) vim.snippet.expand(args.body) end },
      sources = { { name = 'nvim_lsp' }, { name = 'zsnip' } },
    })
<
The `snippet.expand` line is what makes nvim-cmp use Neovim's engine. nvim-cmp
is required by `register()` only, so the module loads without it.

                                                     *zsnip.start_lsp_server()*
zsnip.start_lsp_server({opts})

Start an in-process language server answering `textDocument/completion` with
the snippets of the requesting buffer's filetype, and attach it to the
buffers that qualify. Idempotent: calling it again stops whatever a
previous call started, clients included, before starting the new one.

A buffer holds the client when it has a filetype, has no 'buftype' (prompts,
terminals, :help, ...), and, if `filetypes` is given, its filetype or one of a
dotted filetype's dot-separated components is on the list. This gate re-runs
on every FileType, so a buffer that stops qualifying loses the client it
already has, not only one that never gets one.

Options:
    name                string    Client name, as it appears in `:checkhealth vim.lsp`
                                  (default "zsnip")
    filetypes           string|string[]  Attach only to these filetypes, or a dotted
                                  one's dot-separated components ("javascript"
                                  also attaches to "javascript.glimmer")
    limit               number    Cap on items per response: a non-negative
                                  whole number, or `math.huge` for no cap
                                  (default: uncapped)
    documentation       boolean   Attach the body as item documentation
    filter              fun       Keep only the snippets it returns true for
    trigger_characters  string|string[]  Characters that make a client ask unprompted
    completion          boolean|table  Wire each attached buffer up for
                                  |vim.lsp.completion|; a table is forwarded
                                  to its enable()

`completion` is what makes an accepted item expand. Attaching a client is not
enough: the handler that reads `insertTextFormat` is installed only by
vim.lsp.completion.enable(), so without it the items arrive and accepting one
puts a literal `${1:mod}` in the buffer. It is applied to zsnip's own client
only, never to your language servers.

The server answers on the next tick rather than inline. Being in-process makes
a synchronous reply possible and it is wrong: |vim.lsp.completion| drives
'omnifunc', which returns -2 to say "the items come later" precisely because
textlock forbids |complete()| while the option is being evaluated.

blink.cmp and nvim-cmp can receive the snippets this way too, through their
existing LSP source, at the cost of no longer being able to configure snippets
separately from language-server items. For Neovim's own completion with
`autotrigger`, name the trigger characters -- |vim.lsp.completion| reads them
to decide when to ask unprompted:

A trigger can begin with any printable character -- `2x1table` and `#!` are
both real friendly-snippets triggers -- so a letters-only list leaves the first
firing a keystroke late and the second never firing at all. This decides only
when the client asks; which items are offered, and what each one replaces, is
settled by the textEdit zsnip sends. With <C-x><C-o> it is not needed at all.
>lua
    local triggers = {}
    for byte = 33, 126 do
      triggers[#triggers + 1] = string.char(byte)
    end

    require('zsnip').start_lsp_server({
      trigger_characters = triggers,
      completion = { autotrigger = true },
    })
<
                                                      *zsnip.stop_lsp_server()*
zsnip.stop_lsp_server()

Stop it again: the autocmd that attaches the server goes, and so do the clients
it attached. Idempotent, and the exact undo of |zsnip.start_lsp_server()|.

`require('zsnip.lsp').started()` reports whether the attaching autocmd is
installed, and `require('zsnip.lsp').running()` whether a client is actually
up -- registered is not the same as serving.

                                                              *zsnip.complete*
Neovim's built-in completion~
>lua
    require('zsnip.complete').enable()

    vim.o.autocomplete = true      -- optional; CTRL-N reaches it either way
    vim.o.completeopt = 'menu,popup,noinsert,fuzzy'
<
A function source in 'complete', so snippets rank next to buffer words in one
menu and 'autocomplete' drives them as you type. No completion plugin and no
LSP client: enable() appends one entry to 'complete' and installs two handlers
-- a |CompleteDone| expander, which only fires on an accepted item (<C-y>, or
a mapping that sends it; <CR>, <Space> and <Tab> are `discard` in Vim, same as
a typed character or <Esc>, and never expand), and a |CompleteChanged| stylist
for the preview. Because 'complete' is buffer-local, enable() appends to the
global default and to every buffer already open, not just the current one, so
lazy-loading it on InsertEnter still reaches buffers that were open before
that fired.

Each source can be capped on its own. Setting 'complete' yourself means enable()
should not append to it as well, so take the entry from source() and pass
`complete = false` -- that installs only the handlers: >lua
    vim.o.complete = ".^5,w," .. require('zsnip.complete').source() .. '^10'
    require('zsnip.complete').enable({ complete = false })
<
enabled({bufnr}) and disable() read the entry with or without its `^{count}`,
so a capped setup is recognised rather than appended to twice; enabled()
defaults {bufnr} to the current buffer, since 'complete' is scoped to it.

enable() takes the same `limit`, `documentation` and `filter` as the other
sources -- except that `limit` defaults to `max_items` here rather than to
uncapped, since nothing downstream trims what this source returns.
The preview shows exactly what |vim.lsp.completion| would render for the same
snippet: the description as prose, then the body syntax-highlighted -- the
same markdown the LSP-shaped sources put in `documentation`, styled the same
way (treesitter over the preview float, fences concealed) by the
|CompleteChanged| handler. The styling reaches the float that `popup` in
'completeopt' opens -- the `preview` split shows the markdown raw -- and
comes back off when selection moves to another source's plain item, since one
menu reuses the same float -- except while an item served by
|vim.lsp.completion| is selected, which core restyles on its own schedule and
zsnip leaves alone; it comes back off as usual on the next plain item. The
menu row stays the trigger and its kind alone.
`description_style = 'classic'` keeps the description in the menu row instead,
visible without selecting, with the preview holding a plain body.
`documentation = false` empties both wherever they went, and disable() undoes
everything enable() did. It deliberately leaves 'autocomplete' alone --
whether the menu opens by itself is your decision. With it on, an empty base
returns nothing: the whole filetype is not a useful menu after every space,
and Vim's own `.` source shows nothing there either. A manual CTRL-N with
'autocomplete' off still lists the lot.

An `expand` function replaces |vim.snippet.expand()| as what turns the
accepted body into a session -- for a caller whose user chose a different
engine somewhere else. The trigger is already deleted by the time it runs.

Two things are specific to this path. zsnip does the matching, returning
`refresh = "always"` so it is re-asked on every change -- and without `fuzzy`
in 'completeopt' Vim narrows the result again by its own plain-keyword rule,
so a hit whose `word` is not a prefix of the keyword under the cursor
(`clog` for `console.log`, `rq` for `req`) is filtered back out and never
shown at all. And zsnip does the expanding, since nothing else here knows
what a snippet body is -- the range it replaces is the whole non-blank run
before the cursor, because a third of real triggers mix words and symbols
(`console.log`, `<div`, `#!/usr/bin/env`). A trigger typed after a bracket
still works: `(req` keeps the `(` and expands `req`.

                                                     *zsnip.completion_items()*
zsnip.completion_items({opts})

Snippets as `lsp.CompletionItem`s, for a hand-rolled completion source. Items
carry `insertTextFormat = Snippet` and a resolved `insertText`. One item per
trigger.

Options:
    prefix         string   Fuzzy-match triggers against this
    filetype       string   Defaults to the filetype of {bufnr}
    bufnr          integer  Defaults to the current buffer
    position       table    lsp.Position the response is anchored to; defaults
                             to the real cursor when {bufnr} is the current
                             buffer
    limit          number   Overrides `max_items`: a non-negative whole
                            number, or `math.huge` for no cap
    documentation  boolean  Overrides the configured default
    filter         function  Keep only the snippets it returns true for;
                             runs before matching and before `limit`

Items also carry a `textEdit` naming the span to replace: the whole non-blank
run before the cursor. Left to pick that span itself a client picks the keyword
before the cursor, which is not what a trigger is -- `<div` would be filtered
out for not matching the prefix `div`, and `#!` would be inserted in front of
its own expansion rather than over it. Every item in a response shares one
span, because |vim.lsp.completion| filters the whole list against the lowest
start it is given. Text in the run that the trigger does not account for -- the
`(` of `(req` -- goes back in front of the body, escaped so it stays text; it
also goes into `filterText` when some suffix of the run actually matched the
trigger, and not otherwise, so a prefix-filtering client does not offer every
snippet after a bare `(`. How much of the run counts as such text is decided
per legal start of the run, longest first: the first one the trigger
fuzzy-matches from -- whether that start began the trigger outright or only
fuzzy-matched it -- is where that text ends. `(c.log` against `console.log`
keeps `(`, since the match starts one byte in, at `c.log`; `c.c` against
`console.clear` keeps nothing, since the match already starts at the run's
first byte.

A `textEdit` needs a cursor to anchor to. There is none when {bufnr} is not the
current buffer and no {position} was given; the items are then plain.

8. API                                                              *zsnip-api*

                                                                  *zsnip.get()*
zsnip.get({filetype})
    Every snippet available to a filetype (its own, then inherited, then each
    dot-separated component of a dotted filetype, then global), in shadowing
    order. Defaults to the current buffer's filetype. Each entry carries a
    `filetype` field naming where it came from.

                                                            *zsnip.available()*
zsnip.available()
    Every filetype zsnip knows snippets for, mapped to them.

                                                              *zsnip.resolve()*
zsnip.resolve({body})
    Resolve the variables Neovim does not know in an arbitrary body. Handles
    $VAR, ${VAR}, ${VAR:default} and ${VAR/regex/format/}; the last two
    collapse to the plain value, since |vim.snippet.expand()| discards the
    default and implements no transforms. A name zsnip does not know is left
    exactly as written.

                                                              *zsnip.version*
zsnip.version
    The plugin's own version, e.g. `'0.1.0'`. Reported by |:checkhealth| zsnip.

                                                               *zsnip.reload()*
zsnip.reload()
    Forget everything read from disk; the next lookup rescans. Snippets added
    through |zsnip.add_snippets()| survive.

                                                                *zsnip.match()*
zsnip.match()
    The snippet whose trigger ends at the cursor, longest trigger first. A
    trigger starting with a keyword character has to start a word, so `x` does
    not fire in the middle of `max`.

                                                           *zsnip.expandable()*
                                                               *zsnip.expand()*
zsnip.expandable()
zsnip.expand()
    Whether the trigger before the cursor can be expanded, and expanding it.

                                                       *zsnip.expand_snippet()*
zsnip.expand_snippet({snippet})
    Expand a snippet table at the cursor, trigger or not.

                                                       *zsnip.expand_or_jump()*
zsnip.expand_or_jump()
    Expand what is under the cursor, otherwise jump to the next tabstop. The
    one binding most configs want:
>lua
    vim.keymap.set({ 'i', 's' }, '<C-k>', function()
      require('zsnip').expand_or_jump()
    end)
<
                                                                 *zsnip.jump()*
                                                             *zsnip.jumpable()*
                                                               *zsnip.active()*
                                                                 *zsnip.stop()*
zsnip.jump({direction})
zsnip.jumpable({direction})
zsnip.active({filter})
zsnip.stop()
    Thin wrappers over |vim.snippet|, so a config can bind one namespace.
    `jump()` returns whether it moved.

zsnip installs no keymaps of its own -- every completion engine already has an
opinion about <Tab>.

10. HEALTH                                                       *zsnip-health*

>vim
    :checkhealth zsnip
<
Reports the Neovim version, whether |vim.snippet| and the snippet grammar are
available, which loaders are registered, and how many snippets were actually
found.

The last section, "Completion sources", answers the other half of "why do I
see no snippets": a snippet that was found still has to reach a menu.

Two of the four wirings can be detected: the in-process LSP server, and
|zsnip.complete|. For the server it reports whether a client is actually
running, not merely that start_lsp_server() was called -- a `filetypes` list
that excluded every buffer, or a `:LspStop`, leaves it registered and serving
nothing. It also warns when both are on, which offers every snippet twice.

A blink.cmp or nvim-cmp source is registered inside an engine that need not be
loaded when the check runs, so "no source detected" is the correct result when
you use one of those.

11. COMING FROM LUASNIP                                         *zsnip-luasnip*

The loader and registry API is deliberately shaped like LuaSnip's:

    luasnip.loaders.from_vscode.lazy_load()  ->  zsnip.loaders.from_vscode.lazy_load()
    luasnip.loaders.from_snipmate.lazy_load()->  zsnip.loaders.from_snipmate.lazy_load()
    ls.add_snippets(ft, ...)                 ->  zsnip.add_snippets(ft, ...)
    ls.filetype_extend(ft, ...)              ->  zsnip.filetype_extend(ft, ...)
    ls.expand_or_jump() / ls.jumpable()      ->  zsnip.expand_or_jump() / zsnip.jumpable()

LuaSnip's snippet node DSL (`s`, `i`, `t`, `f`, `c`, `d`) has no equivalent:
|vim.snippet| takes a snippet body as text and owns the session, so a body is
either LSP snippet syntax or a function returning it.

vim:tw=78:ts=8:noet:ft=help:norl:
